# Critique: isolated-dev (Go rewrite, v2)

Reviewed at commit `e792f77`. ~20.4k lines of Go across 25 packages, 24 test
files, plus README / QUICKSTART / USAGE / ROADMAP / PARITY. Build was not run
locally (go.mod pins Go 1.26 and the toolchain download is egress-blocked in
this environment, which is a small irony given the tool), so the code findings
below come from reading source and are cited by file:line. Every "confirmed"
item was checked directly.

## Verdict up front

This is a good project with a clear thesis and unusually honest docs. The
security model is the right one, the hard primitive (egress by network
topology, not by env vars) is built and mostly correct, and the code quality
in the lower layers is well above average. The problems are concentrated in
one place: the CLI glue layer, where several security promises the lower
layers make are not actually wired up. A few of those are the kind of gap that
undermines the product claim ("automatic security"), not just a rough edge.

For a first version of the rewrite this is a strong base. The priority should
be closing the promise/behavior gaps before adding surface, because right now
the docs describe a stricter tool than the binary is.

---

## What is genuinely good

**The core idea is sound and differentiated.** "Deny by default, opened one
deliberate step at a time, per project, revocable" is the right shape for the
problem, and the egress design is the real thing: the workload sits on an
`--internal` docker network with no route out, a dual-homed proxy sidecar is
the only path, and DNS resolves only through a filtering resolver. That means
a process ignoring proxy env vars does not fall through to the open internet,
it has no route at all. Compared to the common "set HTTP_PROXY and hope"
approach, this is a topology boundary rather than a convention. That is the
uniqueness.

**The single best check in the codebase is correct and tested.** IP literals
are denied unless a rule names the address, and a hostname rule explicitly
never authorizes a literal (`internal/netpolicy/allowlist.go:109-139`). This
closes the "resolve the name yourself, then dial the address to sidestep every
hostname rule" bypass, and the test names that exact threat
(`proxy_test.go:228`). Bare hostname grants open only 80/443, so
`allow github.com` cannot silently become an SSH tunnel. Deny-by-default even
on a nil policy. These are the things a naive implementation gets wrong.

**No TLS interception, and it is honest about the cost.** The proxy relays
bytes untouched, so cert pinning keeps working and it never holds anyone's
plaintext. A real TLS handshake is driven end to end in the tests to prove no
interception (`proxy_test.go:155`). The ROADMAP then states plainly what this
gives up (per-host, not per-path filtering) and why injecting credentials
(the Docker Sandboxes approach) was rejected. That section is the strongest
piece of writing in the repo.

**The threat model is stated without overclaiming.** Section 4.4 of the
ROADMAP separates "accidental exfiltration" (contained) from "determined
adversary through an allowlisted host" (not contained), and calls out the
agent's own API channel as an uncloseable bidirectional path. The docs
repeatedly say "TOFU covers what the project is granted, not what its code
does." A security tool that resists the urge to oversell is rare and it builds
trust in the parts that do work.

**RunSpec kills the v1 bug class.** The whole "assemble an argv from strings"
defect family is designed out: one typed struct, one renderer
(`container/runspec.go:130`), golden tests on the vector including
env-with-spaces, env-with-newline, and comma-in-mount-path. Mount validation
refuses a comma in a path because someone actually hit it with 1Password's
"Group Containers" (`runspec.go:229`). This is the justification for the
rewrite, and it is delivered.

**Failure-mode engineering is a cut above.** `explainExit` turns a dead
sidecar into "your image is older than your binary, run `make proxy-image`"
(`sidecar.go:188`). Port-already-allocated names the culprit container and the
fix. `dev scan` treats "no scanner" as a failure, not a pass. `doctor`
diagnoses but refuses to mutate. These are the details that decide whether a
security tool gets kept or switched off.

**Docs are worked-example first and admit the awkward parts.** QUICKSTART
covers monorepos, production-Dockerfile-as-dev-image, and the 7GB build
context problem directly. That is the difference between docs written for the
reader and docs written for the author.

## What is bad, in rough order of how much it undermines the claim

### 1. Security promises the code does not keep (the important category)

These matter most because the product claim is "automatic security." Each is
verified in source.

**`--safe` is dead.** `dev agent run claude --safe` is meant to keep the
agent's own permission prompts instead of auto-approving. The flag is declared
and bound (`cli/agent.go:154,249`) but never assigned to `opts.Safe`, so
`agent/run.go:233` still passes `--dangerously-skip-permissions`. The cautious
user gets YOLO mode. Worse, the unit test `TestSafeModeDropsAutoApproveArgs`
passes, because it exercises the spec builder directly and never goes through
the CLI, so the suite gives false confidence about exactly the flag a careful
person reaches for. This is the single most important bug in the repo.

**Machine policy is not enforced on most routes in**, despite the package doc
and ROADMAP M4 both claiming "every route in." `policy.CheckHost` is called
only from `dev agent allow` (`allow.go:49`). It is not called from
`--allow-host` on run/shell/console/agent, from the interactive "allow this
project from now on" prompt (which also persists the grant), or from
`dev agent accept`. And `runAgent` never loads policy at all
(`cli/agent.go` has no `loadPolicy` call), so `network_modes`, `forbid`, and
`require.memory` do not apply to agent runs, the run type with the most reason
to be constrained. A deny_hosts entry can be walked straight around.

**Consented grants that do nothing.** `mount_ssh_keys`, `mount_git_config`,
`mount_docker_socket`, and `pass_env_vars` are parsed
(`config/config.go:67-71`), described to the user in the consent prompt, gated
behind `dev accept`, and reported by `doctor` and `migrate`. They are never
read by `project.RunSpec` (no consumer in `internal/project`). So the trust
prompt asks the user to authorize things that have no effect, which is exactly
the "prompt that protects nothing" failure the ROADMAP warns against. Either
wire them up or delete them from config and consent. The ROADMAP 4.1
trust-level table (untrusted/trusted/privileged) has no representation in code
at all.

**Accepted egress hosts do not apply to plain runs.** `dev agent accept`
records a project's requested `allow_hosts`, but `dev run` / `dev shell`
build the allowlist as `Registries() + Resolve("default").AllowHosts` and omit
`store.AcceptedRequest(...)` (`workspace.go:362`, `console.go:160`), which the
agent path does include (`agent.go:353`). So a user accepts the project's
hosts, then finds `dev run` still blocked by them. Silent divergence between
two commands that should agree.

**No SNI enforcement, but the docs say there is.** ROADMAP:228 and :328 claim
"allowlists by CONNECT target / SNI hostname" and "SNI-allowlisting proxy."
There is no ClientHello / ServerName parsing anywhere outside test fixtures.
Only the CONNECT authority is checked, then bytes are relayed untouched. For a
CDN-heavy default allowlist (githubusercontent, registries) this leaves domain
fronting open: CONNECT to an allowed front, send a different SNI/Host inside
the session. SNI checking is precisely what would close it, and it is claimed
but absent. Either implement it or correct the docs, because a reader reasons
about the boundary from that sentence.

### 2. Enforcement gaps in the proxy itself

- **Pre-existing network is trusted blindly.** `NetworkCreate` swallows
  "already exists" (`engine.go:167`) without checking the existing network's
  `Internal` flag. A leftover network created without `--internal` (crashed
  run, old version, name collision) gives the workload a default route and
  fully open egress while the CLI still reports `network: allowlist`. The
  whole model rests on that one flag and it is never re-verified. One
  `docker network inspect -f '{{.Internal}}'` closes it.
- **Wildcards have no public-suffix guard** (`allowlist.go:79`). `*.co.uk`,
  `*.github.io`, `*.s3.amazonaws.com` all parse and match at any depth. A
  grant of `*.github.io` is "all of GitHub Pages"; `*.co.uk` is a TLD.
- **Wildcard grants reopen DNS exfiltration.** For an allowed name the full
  QNAME is forwarded upstream verbatim (`resolver.go:77`), so with
  `*.example.com` granted, `<payload>.example.com` A-queries carry data out
  and are logged as `allow`. The A/AAAA-only restriction closes TXT tunnels
  but not label-encoded exfil, which needs no answer.
- **The interactive grant ignores the port it asked about.** `prompt.go:106`
  grants the bare host, which defaults to 80/443. Approve `evil.com:8080` and
  you open 80/443 (never asked about) while the request you approved keeps
  failing because `Allows(host, 8080)` stays false and it times out. Wrong in
  both directions, invisible from the prompt.
- **No SSRF guard on the dial target** (`proxy.go:110`): no RFC1918 /
  loopback / link-local / 169.254.169.254 filter. Any allowlisted name whose
  DNS the attacker influences becomes a route to the docker gateway, host, or
  metadata endpoint.

### 3. Robustness bugs that will bite normal use

- **`IdleTimeout` is an absolute 10-minute lifetime, not an idle timer**
  (`proxy.go:385`, default `proxy.go:81`, never overridden). The deadline is
  set once before the copy loops and never refreshed on activity, so every
  tunnel dies at 10 minutes even under continuous transfer. That kills exactly
  the tool's own traffic: long agent streaming sessions, big `git clone`s,
  `ssh` through the ProxyCommand. The field doc even says "inactivity," which
  is not what it does.
- **Forward relay teardown can hang forever** (`forward.go:117,131`): no
  deadlines on the copy, and `Close()` does `wg.Wait()`, so one idle
  forwarded connection blocks teardown indefinitely. The comment claims a
  refused connection is reported to the client; the code silently drops it
  (`forward.go:92-98`).
- **`runPTY` swallows exit codes** (`runner.go:189-197`): the `default` branch
  returns `Result{}, nil`, so a console/pty workload killed by a signal or
  failing for a non-ExitError reason reads as exit 0, success.
- **A fresh `http.Transport` per plain-HTTP request, never closed**
  (`proxy.go:264`): leaks fds and goroutines under a request loop.
- **Exit codes flattened to 1** (`root.go:139`): `dev run -- make test` cannot
  propagate the test's real exit code, which hurts the CI story the tool
  otherwise argues for.

### 4. Distribution is a blocker, not a polish item

The sidecar image can only be built via `make proxy-image`, which is
`orb -m <vm> sudo docker build` against the repo root (`Makefile:52`). A user
who installs the release binary has no repo and cannot build the sidecar,
which is mandatory for every allowlist run (`agent.go:577`). So the flagship
feature does not work from a clean install today. Embed the Dockerfile in the
binary, or publish the image, before any release. `ensureProxyImage` also
accepts any locally-tagged `dev-proxy:latest` with no digest check, so a stale
sidecar is used silently.

### 5. Command surface will irritate users

- **`dev agent allow / revoke / grants / config` are not agent-specific.**
  A plain `dev run` that gets blocked tells the user to type
  `dev agent allow HOST` (`workspace.go:368`), and plain runs consume those
  grants. Four of nine `dev agent` subcommands have nothing to do with agents.
  They should live at the root (`dev allow`, `dev grants`). This is the
  friction point most likely to make people mutter at the tool daily.
- **`dev accept` vs `dev agent accept` split** is real and deliberate
  (settings vs egress hosts), but combined with gap #1.4 above it is a trap:
  the two do different things, and one of them silently does not apply to the
  command you were using.
- **Error message points at a nonexistent command**: `orbstack.go:76` says
  "create it with `dev env up docker-host`"; there is no `dev env`.
- **`--egress-notify` is unvalidated** (`agent.go:251`): anything not exactly
  "off" means on, so `--egress-notify of` silently does the wrong thing.
- **`--dry-run` runs too late** (`agent.go:421`): a clone is already created on
  disk (`agent.go:199`) before the dry-run check.
- **`--allow-push` hardcodes `github.com:22`** (`agent.go:320`) regardless of
  the actual remote, so GitLab/Bitbucket users get a grant that cannot work
  and a warning naming the wrong host.
- **Stale language docs**: `languages/README.md` documents `dev list`,
  `--init`, `--devcontainer` flags that do not exist in v2.

### 6. Portability leaks

The Backend interface is real but thin, and the CLI bypasses it. `Env.driver()`
returns the concrete `*orbstack.Driver` (`root.go:39`) from 12 sites, there is
no backend selection or auto-detect, `dev vm start` shells straight to
`orb start` (`status.go:312`), and `internal/backend` has no tests. None of
this is wrong for an OrbStack-first M1, but the "plain docker backend" of M3
is more than a driver file: it is also the doctor text, the VM command, and
the distribution path above.

## Uniqueness and usefulness, assessed

Useful: yes, clearly, for the stated jobs. Running untrusted dependency
updates, sandboxing an agent, and inspecting a suspicious binary are real
recurring needs, and the tool's answer to each is better than hand-rolled
docker. The `--clone` workflow (agent works in a private copy, you review a
diff and fetch it back) is a genuinely good idea well executed.

Unique: the egress-by-topology model plus no-TLS-interception plus
per-project revocable trust is a combination the obvious alternatives
(plain devcontainers, Docker Desktop, ad hoc `docker run`) do not offer.
Docker's own sandbox product is the closest comparison, and the ROADMAP's
analysis of why it rejects credential injection is credible. The risk to
uniqueness is scope: the moment this tries to be a compose replacement or a
multi-backend orchestrator it stops being "the simple secure sandbox" and
starts competing with tools that have more people on them. The ROADMAP's
"deliberately out of scope" list is the right instinct; hold it.

The tension worth naming: the pitch is "automatic security with as little
hassle as possible," but the honest version of this tool has real hassle
(first run blocked, grants to make, builds unfiltered, ports that do not
publish in allowlist mode). The docs handle this well by reframing the
friction as the product. Keep doing that. The failure mode is a future
version that quietly widens defaults to reduce complaints and loses the thing
that made it worth using.

## Prioritised recommendations

### P0 - correctness of the security claim (do before any release)

1. Wire `--safe` to `opts.Safe`, and add a CLI-level test
   (`dev agent run --safe --dry-run` asserted against the fake runner). The
   current green test is worse than no test.
2. Either apply the mount / pass-env grants in `project.RunSpec`, or remove
   them from config and consent. A prompt that authorizes nothing trains users
   to click through the prompt that matters.
3. Route every allowlist mutation and every accepted host through
   `policy.CheckHost`, and call `loadPolicy` in `runAgent`. "Every route in"
   should be true or the sentence should go.
4. Include `store.AcceptedRequest(...)` in the `dev run` / `dev shell` /
   `dev console` allowlist so accepted hosts actually apply.
5. Verify the existing network's `Internal` flag on the already-exists path.
   Silent full-egress bypass is the worst outcome the tool can have.
6. Resolve the SNI mismatch: implement CONNECT-time SNI checking, or correct
   ROADMAP:228/:328 and the sidecar comments to stop claiming it.

### P1 - it works from a clean install and does not break normal use

7. Ship the sidecar without the repo: embed `Dockerfile.proxy` in the binary
   or publish the image, and digest-verify it in `ensureProxyImage`.
8. Fix `IdleTimeout` to refresh on activity (or rename it and add a real idle
   timer). Today it silently kills long clones and agent sessions.
9. Fix `runPTY` exit-code swallowing and stop flattening all errors to exit 1
   so `dev run -- <cmd>` propagates status for CI.
10. Add deadlines to the forward relay and make `Close()` not block forever.

### P2 - stop irritating the user

11. Move `allow` / `revoke` / `grants` / `config` to the root; keep `dev agent`
    for agent-only verbs. Update the blocked-run hint text to match.
12. Fix the `dev env up` error string, validate `--egress-notify`, move the
    `--dry-run` check before clone creation, and derive the push host from the
    repo remote instead of hardcoding GitHub.
13. Correct `languages/README.md` and any doc that names a nonexistent flag.

### P3 - hardening and future ideas

14. Public-suffix guard on wildcard parsing, and surface `*.tld` grants as a
    warning in the prompt.
15. QNAME length / label-count heuristics on forwarded queries under wildcard
    grants, since that is the DNS exfil path the current design leaves open.
16. SSRF filter on the proxy dial target (block RFC1918 / loopback /
    link-local / metadata) unless a rule names the address.
17. IDNA / punycode normalization and a homoglyph check in the grant prompt,
    the one UI where a user widens policy by reading a hostname.
18. An integration tier against a real docker daemon in Linux CI (the backend
    interface exists specifically to make this possible), plus end-to-end
    tests through the fake runner for `runAgent` / `runWorkspace`. Every P0 bug
    above survived a green suite because the tests stop at the glue layer.
19. Bound the attacker-keyed maps and log volume in the sidecar and the host
    watcher (a retrying client can emit thousands of distinct denials).
20. The "plain docker interface" from the ROADMAP: treat it as driver + doctor
    text + `dev vm` semantics + distribution, not just a driver.

---

## One note on the docs

The docs are a strength, but right now they are ahead of the binary in several
places: SNI, "policy fixed at start" vs the control socket that ships on by
default, "every route in," NXDOMAIN vs the (better) REFUSED the code actually
returns, and the `IdleTimeout` "inactivity" wording. As the UI/UX refresh and
the updated ROADMAP land, the highest-value edit is to make every security
sentence match the code, or file the gap. The tool's credibility with the kind
of user who would adopt it rests more on that than on any feature.
